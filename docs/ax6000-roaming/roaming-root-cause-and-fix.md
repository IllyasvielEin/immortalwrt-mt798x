# AX6000 漫游故障：根因范围与修复方案

2026-11-08。已完成两轮实机故障/恢复记录及匹配版本源码审查。本次仅下载源码和只读核对，没有修改固件代码、编译、推送、刷机或再改路由器配置。当前 AX6000 k/v/r 为 0/0/0，诊断已关闭。

**已确定阻断连接的驱动机制；尚无经过构建和真机验收的修复。** 旧关联为何未在漫游时立即失效，仍有离网通知方面的证据缺口。可以针对已定位的错误转发做修复实验，不必先假设平板或 GS7 有协议错误。

## 已证实的机制

平板 `.32` 从 AX6000 到 GS7 后，Linux 桥已将其 MAC 学到 `wan`，固定端 `.13` 留在 AX 的 `rax0`。平板 SYN 经有线到达 `.13`，固定端的 SYN-ACK 返回 AX 无线驱动时，驱动仍查到平板旧 `SST_ASSOC` / WCID 4，选择 `sta-same-wdev/to_os=0/to_air=1`。回包没有交给 Linux 桥，被提交给已经失效的本机无线目的条目；因此正确的桥表无法挽救。

关闭 11k 并重载后重新建立相同位置条件，仍有两条新 TCP 连接重复此路径。旧 STA 自然老化删除后，驱动改为 `lookup-miss/to_os=1/to_air=0`，`wan` 捕获到匹配的 SYN-ACK，用户也明确确认两轮均恢复。关闭 k 未解决此故障；v/r 本来关闭，不能把继续切换它们当作已定位的根治措施。

原始证据：`evidence/roam-20261108-163317/`，以及 `evidence/roam-k-off-20261108-1735/failure-summary.json`、`recovery-summary.json`。新连接匹配使用四元组、TCP seq/ack，未用切换前握手或主线程反向探测冒充业务失败证据。

## 精确源码已核对

完整源码位于 `../sources/vendor-mt79xx-7.6.7.3/source/mt_wifi/`。归档 SHA-256 为 `b029d7b43c498193092dc6a3c857361c8835ce34bb306561c550ac0539784a78`，与诊断分支及当前生产配方相同。原始解包未打补丁；同时审阅仓库补丁差异，当前生产与诊断分支的 7673 补丁集合仅相差诊断 043。

- `embedded/ap/ap_data.c:4078–4094`：仅凭 `MacTableLookup`、`SST_ASSOC`、同 `wdev` 就令 `to_air=TRUE/to_os=FALSE`，没有查询 Linux 桥 FDB。
- `embedded/common/cmm_data.c:3608–3635`：只有返回 `to_os=TRUE` 才继续上送协议栈；与抓取结果一致。
- 当前 `999-ppe-08-mtk_ppe-add-roaming-handler.patch` 清理目标 MAC 对应的 flowtable/硬件卸载流，不处理 MTK 站点表，也不改变上述内部转发分支。该补丁在诊断分支和生产 HEAD 一致，不能拿它当本问题已有修复。
- 驱动确有部分移动旧条目删除逻辑，但所查位置 `ap_data.c:3695`、`cmm_data.c:5742` 限定 A4/MWDS/APCLI 四地址无线接收路径，不能外推到本次普通有线回程。

## 为什么两轮都在 idle=492 时清理

`max_idle_period` 单位为 **1000 TU，即每单位 1.024 秒**（`embedded/include/rtmp.h:3098`）。新 STA 在 `embedded/mgmt/mgmt_entrytb.c:1418` 复制 BSS 值到自身 `StaIdleTimeout`。一秒维护由 `embedded/ap/ap_mlme.c:255` 调用，`embedded/ap/ap.c:3897` 判断：

```c
NoDataIdleCount > (StaIdleTimeout * 1024) / 1000
```

现场 480 对应整数阈值 491，首次超阈值为 **492**，完全解释两轮日志。因此不能再把 480 原始字段直接当作精确 480 秒，也不能把等待归因于老化计时失效。计数可被接收、部分发送成功或 PS 指示重置，漫游时间不等于计时起点。

另一个修正：Build 19 的 `CONFIG_MTK_DOT11_HE_AX=y`、`CONFIG_MTK_WIFI_TWT_SUPPORT=y` 已核实。当前 `ap.c:3908/3974` 分支只保护实际 TWT bitmap 非零者；现场 `twt=0`。旧条目的 `ps=1` 不足以说明本版跳过了失联踢除，也不能证明平板当时真的休眠。两轮 `tx_fail=0/7` 也不涵盖全部发送失败条件，默认 `EntryLifeCheck=1024`，不应套用旧驱动教程。

## 首选：可动态开关的桥转发实验

先做诊断专用分支的小范围候选，保留现有分区、认证和 k/v/r 条件。新增默认关闭的运行时开关，仅选定 `.13` 与平板这对 MAC 的普通同 BSS 单播。在既有源站点授权、隔离等安全判断通过，且原结果确为 `to_air=1/to_os=0` 后、复制/提交无线包之前，改为 `to_air=0/to_os=1`，由 Linux 桥选择出口。

覆盖该 MAC 对的**全部 L2 单播**，不能只放行 SYN/SYN-ACK，否则握手通过后数据仍会被截走。保持跨 BSS、VLAN、A4/WDS、组播及隔离的既有行为；拒绝分支不得被覆盖。客户端源 MAC 与接收站点/WCID的一致性、授权检查必须保持。此机 19:14 只读核验 `br-lan vlan_filtering=0`、`rax0 hairpin=1`；hairpin 支持两终端同在 AX 时经桥回发同无线接口。

在新一轮故障仍存在、旧条目仍在时执行开→关→开的对照，期间不重载无线、不清 STA、不改 k/v/r、不改 FDB：

1. 关闭时复现旧条目错误直转。
2. 开启后预期回包立即交桥、经 `wan` 返回 GS7，并由用户确认新连接恢复，旧条目无需先消失。
3. 若旧条目仍在，关闭后预期同样故障再现；重新开启后恢复。

这比切换配置后重载无线更能验证因果。实验开关与诊断继续隔离在专用分支，不能直接混入生产。通过后，桥转发模式可作为实际修复候选，但还需双向漫游、同 AP 互访、隔离、IPv4/IPv6、TCP/UDP 和性能验证；CPU/无线直转性能代价尚未测量。

Astra复核后补充实机ON前约束：必须是精确双MAC互通，不能复用043的“任一端命中”诊断条件；须结合已应用的041端口安全补丁核实实际RX身份/授权及VLAN元数据。to_os=1后仍有FAST_NAT/WHNAT/WARP等钩子，必须证明实际桥/wan出口及业务成功。开关只回退路径选择，不撤销已产生的学习/连接/缓存状态；若需要目标流缓存失效，须设计对称处理及OFF同等处理对照。完整细则见 [方案取舍](roaming-options-proposal.md)。

## 选择性 FDB 旁路是后续优化候选

仅在 FDB 表明目的 MAC 位于同桥其他端口时上送桥，可保留正常同 AP 直转性能，但还不是安全定案。GS7→AX 返回时，FDB 可能仍指 `wan`；若平板回 AX 后继续内部直转，其源地址不经桥学习，简单优先旧 FDB 可能制造反向黑洞。因此必须处理新鲜接收/关联与源 MAC 学习，验证双向切换，而不是只修 AX→GS7。

内核 6.12.112 的公开 `br_fdb_find_port()` 在 `net/bridge/br_fdb.c:251` 要求 `ASSERT_RTNL()`，不能直接从 RX 软中断调用；外层 RCU 不能替代 RTNL。它还是 GPL-only 导出，现场 MTK 模块 taint 为 `PO`，也不能直接假定可链接。若选择此方向，应在支持的接口契约和模块边界内设计桥协作/控制面同步；增加一层包装本身不解决RTNL或导出限制。不在驱动暴露或缓存桥私有对象；还需处理 VLAN、卸载、返回方向与并发。首轮仅桥转发实验不需要新桥查询 API。

## 已找到的配置缓解及限制

真实配置是 **`BssMaxIdle`**，不是未经核实的通用 `IdleTimeout`：

- DAT 解析在 `embedded/common/cmm_profile.c:8027`；范围为 1–65535，0 回默认 480。运行时 set 在 `embedded/ap/ap_cfg.c:13989`，单位仍是 1000 TU。
- 它可以缩短故障等待，但同样影响正常休眠终端。修改 BSS 值不立即更新旧 STA，需新关联；还须核对 UCI/DAT/DBDC 的应用路径。当前未下发、未真机验证新的值。
- `StationKeepAlive` 注释明确只探活，无响应不直接解除关联；不能把它当快速清旧条目的开关。
- `DisConnectSta=MAC` 是现成的定向干预命令，但需核实本机调用接口、实际删除结果及重关联竞争；适合临时恢复或因果测试，不宜无条件自动踢人。
- `NoForwarding=1/isolate=1` 只把 `to_air` 关闭，不开启 `to_os`，会丢包，不是桥转发开关。

## 尚未确定与检索边界

尚不清楚离网管理帧是终端没发送、AX 未收到，还是更早入口丢弃。诊断已覆盖相关 PMF/BSSID 拒绝和接受分支，两轮未见这些事件，不能认定 PMF 或 GS7 为根因。空口及早期管理帧证据可继续补，但不应将其缺失当作无法验证转发修复的理由。

已查询直接上游最近 10 项 `mt_wifi` 变更，以及 chasey/hanwckf 公开问题的 `漫游`、`roaming` 关键词；在这些范围内未发现可直接 cherry-pick 的本症状修复。最近相关驱动修补为 RX port-security、关联 IE 长度等，不修此分支。未覆盖厂商私有补丁、所有 SDK 与全部第三方 fork；换 mt76/Viking/LEDE 不能据此承诺治愈或直接升级。

长期修复/因果验证优先准备上述动态桥转发候选，但要先落实后述独立审查约束，再依据实验决定生产修复。若仅先求临时缓解，可在工具与覆盖条件成立后做单项RSSI试验；不能以此无限延迟机制实验。当前结论不是“已有验证通过的永久修复”。

用户要求先查业界/社区后，已补充 [社区方案调研](roaming-community-solutions.md)：OpenWrt/mac80211已有条件式关闭内部转发、交Linux桥的实现，支持该候选方向；历史IAPP可借鉴站点同步，但非现成跨厂商配置；DSA层已有已合入修复，不能替代本机MTK内部直转路径。未实施上述候选。

另找到Padavan已合并的低RSSI漫游助手示例（PR#407）。SDK有`kicklow → KickStaRssiLow`源码hook，但最终依赖外部iwpriv；Astra指出构建缺包线索，主线程21:18核验标准PATH与四个标准路径确无iwpriv。此前“源码链路存在即可先用”的建议收紧为：先补齐/验证调用能力，再考虑试验，不是已经可用的配置。它不是converter直接写DAT，命令打印和DAT值都不足以证明运行值。第一轮旧平板显示-83、第二轮-92，不能保证社区-85示例有效；覆盖边缘/反复重连代价也需验证。本轮未安装工具或下发参数。
