# AX6000 CI 编译与缓存

工作流使用全新的 Ubuntu 24.04 runner，保持 MTK U-Boot 110MiB、现有软件包和生产诊断隔离检查。
缓存用于减少重复下载和编译，不代替来源、配置、模块或镜像验收。

## 缓存存放位置

- runner 的 `dl/`：源码归档与 `dl/go-mod-cache`。仍执行原生下载和配方摘要检查。
- runner 的 `.ccache/`：C/C++ 编译对象，保留 3G 本地上限，编译器识别为 `content`。
- GitHub Actions cache：工作流上传上述两个目录，下次按 key 恢复。
  可在仓库的 [Actions → Caches](https://github.com/IllyasvielEin/immortalwrt-mt798x/actions/caches) 查看。
- 固件、配置与观察记录另存为 Actions artifacts，不属于编译缓存。

GitHub 缓存有仓库容量、分支可见范围和淘汰规则，不能当长期备份。
每轮的新 key 包含 run ID 和 attempt，以便保存新形成的对象；不会删除历史远端缓存。
本地 3G 上限仅约束 `.ccache/`，不表示仓库远端历史缓存总共只占 3G。

## 恢复、保存与冷缓存

lookup、restore、save 固定为同一已审查的 actions/cache 提交。
精确恢复须核对返回 key；部分恢复、错误 key 或显式失败会清理并禁存。
标准 action 的空 lookup 结果可能是 miss，也可能是服务不可用，记录为 `miss-or-unavailable`；
确认空目录后允许本轮新构建建立缓存，不声称所有服务异常都能识别。
清理失败会停止准备，不能继续使用状态不明的目录。

普通编译或后置验收失败后，有效下载和对象仍可按独立许可保存；取消任务、准备失败或未实际启动 make 不保存。
保存不依赖可选统计成功，缓存服务或统计上传故障不覆盖真实构建结果。
来源核验和构建输入记录是必需准备步骤，其错误仍使任务失败。

`cold_cache=true` 在全新 runner/构建树中跳过恢复和保存，清空指定缓存，但保留本轮 Go 正常缓存功能。
因为冷缓存模式不保存，需要另外一轮允许保存的 seed，再确认后续同输入 matched-key 才算 warm。
兼容前缀恢复不自动等于同输入热缓存，不能用命中率替代任务总耗时。

## 构建记录与功能边界

`ax6000-build-observations-<run>-<attempt>` 包含输入清单、缓存决策、每次 make 的状态和耗时、
本轮 ccache 统计及 runner/实际工具身份。未取得的传输大小、耗时或峰值内存记为空值，不编造估计。
日志副本或统计故障不会杀死 make，也不会令失败的 make 变为成功。

正式固件 artifact 仅在全部验收后上传，包含配置、来源、实际 Go 身份及镜像校验和。
不恢复整棵 `build_dir/`、`staging_dir/` 或 Go 编译缓存 `tmp/go-build`，也不从旧固件复制内核模块。
优化代码和实际提速分别验收；一次 CI 成功不代表真机启动、漫游或代理功能已通过。

## Go bootstrap 选择

`go_bootstrap` 首次仍默认 `source`；本次验证可显式选择 `external`。
external 仅下载固定官方 Go 1.24.13 linux/amd64 引导工具到 runner 的临时目录，
校验大小、SHA-256、归档路径及实际版本/GOROOT/宿主身份后，跳过多级源码引导链。
最终 Go 1.26.10 和 1.27.3 以及目标代理软件仍从锁定源码编译。
下载或验证失败直接终止，不自动切换模式；source 回退只在下一次全新构建中选择。

packages 的两处 `GOTOOLCHAIN=local` 调用补丁记录在独立 manifest，保持模块校验。
feed 准备会统一验证 Nikki 与 packages 的全部临时树和 live 输入，再逐文件原子替换并保留权限。
验证失败零写入；写入中断可能留下完整 pre/postimage 混合状态，重跑可幂等完成，最终 `--check` 要求全部 postimage。
这不承诺跨文件或跨 feed 的崩溃事务，也不检查 manifest 之外整个 feed 工作区的脏状态。

完整 external 构建与代码审核通过后，才以单独变更考虑切换默认值；不能据一轮编译预先宣称稳定提速。
